# Дорожная карта

## Этап 1: локальная рабочая основа

Реализованы: TypeScript strict, promptfoo с локальным mock provider, реестр 16
категорий, валидируемая схема и 10 демонстрационных задач, учёт usage/цены,
синтетический бюджет до запроса, JSON/JSONL, скриншоты, статические русские HTML
отчёты, baseline/current, тесты, документация. Реальные деньги не расходуются.

## Этап 2: реальные измерения

Подготовлены: единый интерфейс шести подключений, OpenRouter с закреплённым endpoint,
официальные подписочные CLI, ручной импорт, диагностика и dry-run без генерации,
legacy pilot, standard из 16 проверенных задач и smoke 6, транзакционный SQLite
с resume/reconcile, контейнер исполнения, слепой text/vision судья,
обратный порядок, ручная калибровка, совместимость оболочек и проверка через заглушки.
Реальные измерения ещё не проводились; Gemini CLI на машине не установлен.

- Пользователь выбирает конкретные model ID/endpoint, проверяет dry-run и выполняет
  первый запуск. API требует явного бюджета, подписки — официальный вход без API fallback.
- Сверить фактический usage/биллинг клиента с сохранёнными JSON, уточнить различия
  версий/полноту внутренних повторов. Проверить Linux/bubblewrap в целевой среде.
- Замерить цену пяти задач; затем 2–3 выбранные модели. Расходы бенчмарка отделять
  от разработки в Codex и сверять с биллингом. Не сбрасывать неизвестные резервы.
- Подготовить и проверить 40–50 уникальных заданий на все 16 категорий. Для кода
  используется ограниченный контейнер с фиксированными зависимостями и скрытыми
  проверками. Расширить проекты/сценарии и глубину checks, включая DevOps build.
- Провести настоящую ручную калибровку около 10% A/B и спорных пар; относительное
  предпочтение не выдавать за абсолютный pass rate. После калибровки решить,
  нужна ли отдельная абсолютная оценка рубрик.
- Первый полный замер с независимыми попытками; сохранять все ответы и разброс.
  Перепроверять старые/новые ответы одной оценкой после изменения рубрики.
- Устранить/оценить существующие advisories транзитивных зависимостей promptfoo
  до дальнейшего расширения доверенной границы; не применять audit fix --force.

## Этап 3: мониторинг и удобство

- Недельный короткий прогон 10–16 задач с ротацией и видимым покрытием.
- Полный повтор раз в месяц/при смене версии/сигнале в рамках бюджета.
- suspected → свежие повторы → расширение затронутого направления. Статистические
  выводы учитывают зависимость попыток одной задачи.
- SQLite, явный fresh rerun и immutable export уже реализованы. Интерфейс, CSV,
  расписание и публикация — по отдельной потребности.

Эта дорожная карта не создаёт расписания, публикации, аккаунты или рассылки.
