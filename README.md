# Practical Model Bench

Локальная рабочая основа практического бенчмарка. Этап 1 работает **только в mock**:
promptfoo выполняет задания и проверки, а собственный код ведёт токены, синтетический
бюджет, историю и сравнение. API-запросов к моделям и фактических расходов API нет.
Результаты демо не показывают качество реальных моделей.

## Установка и запуск

Нужен Node.js 24 LTS (проект зафиксирован и проверен на 24.16.0). Версии зависимостей
закреплены в package.json и package-lock.json. Установка требует интернета; после неё
демо и сравнение работают локально. API-ключи и `.env` не нужны. Во время mock
внешние fetch/HTTP/TCP-запросы Node.js принудительно блокируются; локальный IPC
инструментов разрешён.

```bash
npm ci
npm run browser:install
npm run typecheck
npm test
npm run bench
```

В Linux при отсутствии системных библиотек Chromium используйте рекомендованную
Playwright команду `npx playwright install --with-deps chromium` в подготовленном
окружении. На этой машине Chromium установлен и демонстрация проверена.

`npm run bench` создаёт **два новых запуска**, baseline и current, по 10 задач
и две попытки на задачу. Затем создаёт отдельное сравнение. В консоли напечатаны
полные пути к HTML-отчётам, `Baseline ID` и `Current ID`.

Откройте любой `report.html` непосредственно в браузере. Сервер и JavaScript не нужны.
Для повторного сравнения скопируйте напечатанные ID:

```bash
npm run bench -- --baseline <Baseline-ID> --current <Current-ID>
```

Угловые скобки означают место для значения: в настоящей команде их не вводите.
Повторное сравнение создаёт новую папку и не запускает модель, браузер или судью.
Команда с отсутствующим ID, изменённым артефактом или одним из двух аргументов
завершается с ненулевым кодом.

Дополнительные варианты:

```bash
npm run bench -- --results-dir ./results-example
npm run bench -- --help
npm run bench:demo
npm run bench:compare -- --baseline <Baseline-ID> --current <Current-ID>
```

Последние две команды — совместимые псевдонимы из AGENTS.md. `--results-dir`
задаёт отдельную историю и отдельный синтетический месячный журнал. Аргументов
для реального провайдера, ключей или платного бюджета нет.

## Задания и оценки

В `src/categories.ts` зарегистрированы все 16 категорий. В `benchmarks/demo.json`
есть десять заданий: форма и FAQ; два контракта API; уведомление и заметка о выпуске;
два перевода; тарифы и панель показателей. Основных направлений пять. Формат ответа
дополнительно оценивается в `instruction-following`, поэтому шесть категорий имеют
задания. Остальные десять явно показаны как **не покрыто**, без баллов и pass rate.

Схема Zod проверяет версии, категории, материалы, критерии и критические требования,
проверки, рубрику, готовность и лимиты. Порог успеха задан до выполнения.
Критический провал блокирует успех независимо от среднего результата.
Эталоны и ошибочные ответы проверяются тестами. Проверки не включаются в промпт.

HTML проверяется Playwright в Chromium при 1440×900 и 390×844: встроенная валидация
формы, подписи, клавиатурное раскрытие FAQ, содержимое и геометрия карточек,
отсутствие горизонтальной прокрутки. Сохраняются настоящие скриншоты.
JSON проверяется по фиксированным данным и контрактам, текст — по фактам, числам,
обязательным элементам и формату. Альтернативный порядок ключей и ошибок допустим.

Дизайн, стиль текста и естественность перевода требуют судьи; он не подключён.
Объективные проверки сохраняются, субъективная часть получает `pending`, итоговый
балл — `null`. Отчёт раздельно показывает итоговый и автоматический pass rate.
Итоговый знаменатель включает только завершённые `passed`/`failed`; рядом видны
`pending` и пропуски. Незапущенная или технически неоценённая попытка не получает ноль.
Общего рейтингового балла нет.

В штатном сценарии baseline содержит 10 объективно ошибочных попыток, current —
одну ошибочную попытку FAQ. В current: 7 полностью пройденных, 1 провал и 12 pending.
Снижение FAQ на 50 п.п. отмечается `suspected`. Это специально заданные данные,
а не обнаруженная регрессия модели.

## Токены, цена и бюджет

Контракт mock usage: `inputTokens` уже включает чтение/запись кеша, `outputTokens`
уже включает reasoning. Нормализация хранит эти подмножества отдельно; итог равен
`inputTotal + outputTotal`. Других провайдерских адаптеров пока нет.

`calls.jsonl` хранит исходный usage и нормализованные поля, источник/полноту,
callId/attemptId/taskId/runId, роль, модель/возвращённую версию, тариф, время,
повтор, ошибку и ссылки на ответ. Локальный кеш готового ответа имеет нулевые
новые токены и цену; его исторический usage сохранён отдельно. Настоящий кеш
promptfoo выключен. Mock-сценарии показывают чтение/запись кеша провайдера,
локальный ответ, reasoning, технический повтор, нулевой и неполный usage.

Все тарифы и токены **synthetic**. `modeledCostUsd` — моделируемая цена;
`incurredCostUsd = 0` и `apiRequests = 0` у каждого вызова. Отдельно учитываются
синтетические отправки, первые вызовы модели, судья и повторы. Вызовов судьи нет.
Расходы разработки проекта в Codex не включаются.

Агрегация идёт по уникальным callId: попытка → задача → primaryCategory → модель
→ запуск/месяц. Пересекающиеся категории не увеличивают деньги и токены.
Цена успешной попытки включает расходы **всех** попыток того же набора, судью
и повторы, делённые на число полных успехов. При нуле успехов или неизвестных
начислениях значение `null`. При неполных данных отчёт показывает известную часть,
а не выдаёт её за точный итог.

`configs/demo.json` содержит только mock-настройки, фиксированную таймзону
`Europe/Warsaw` и синтетические лимиты запроса/задачи/запуска/месяца. Перед первым
вызовом резервируется верхняя цена всего входа, максимального выхода и разрешённых
повторов. Reasoning уже включён в выход; инструментов и судьи нет. Повтор тратит
часть заранее зарезервированного конверта. Без нужного резерва вызова не будет.

Операции журнала синхронны и атомарны внутри процесса. Лимиты округляются вниз,
резерв и начисления — вверх до микродоллара. Успешные известные начисления
замещают резерв; неизвестные удерживают его остаток. Две неполные записи каждого
штатного запуска оставляют 0.022528 USD синтетического резерва до сверки.
Месячный журнал `.synthetic-budget.json` сохраняется между запусками в этом
results-dir, а общий `.bench.lock` исключает одновременные процессы.
Реальный бюджет всегда имеет лимит, расход и резерв **0 USD**.

Чтобы посмотреть `budget_exhausted`, уменьшите `syntheticBudget.runUsd` в конфиге,
затем запустите демо в отдельном results-dir. При полном нулевом синтетическом
бюджете остаётся доступно только бесплатное локальное чтение кеша. Неизвестный
тариф/верхняя граница блокирует запрос. Автоматической «сверки» неизвестных
начислений и сброса журнала нет; для чистого синтетического эксперимента используйте
новый results-dir.

## Артефакты и сравнение

```text
results/
  .bench.lock                       # только во время работы
  .synthetic-budget.json            # изменяемый журнал, отдельно от реальных денег
  <run-id>/                         # новая папка для каждого запуска
    manifest.json                   # версии, хеши, окружение, лимиты, бюджет
    calls.jsonl                     # все вызовы, включая ошибки и повторы
    attempts.jsonl                  # статусы, проверки и оценки категорий
    summary.json                    # все уровни агрегации
    promptfoo.json                  # исходный результат движка
    prompts/*.txt                   # точные промпты с материалами
    responses/*.txt                 # ответы каждого вызова
    checks/*.json                   # доказательства и pending-оценки
    screenshots/*.png               # реальные браузерные снимки
    report.html                     # русский отчёт со ссылками
    integrity.json                  # SHA-256 сохранённых артефактов
  comparisons/compare-<uuid>/
    comparison.json
    report.html
    integrity.json
```

Файлы запуска создаются без перезаписи, integrity проверяется перед сравнением.
Это обнаружение случайных изменений, а не криптографическая подпись или запрет
ручного редактирования. При аварии остаются частичные артефакты и `failure.json`;
такой запуск не считается полным. Lock снимается штатно и при обработанной ошибке.
После аварийного завершения сначала проверьте PID в `.bench.lock`; программа сама
не удаляет чужой/устаревший lock и не освобождает неизвестные расходы.

Compare использует совпадающие задания, промпты, материалы, настройки и версию
оценки. Пропущенные пары не входят в качество, но расходы технически неудачных
попыток сохраняются в сопоставимом наборе. Смена оболочки/реализации/окружения
помечается как сравнение систем; смена оценки исключает сравнение качества.
Показаны размер набора, число пар попыток, изменения по категориям и неизвестность.
Повторы одной задачи не объявляются независимыми наблюдениями; статистической
уверенности и выводов о внутренней причине изменения нет.

## Проверки и ограничения

`npm test` включает нормализацию, двойной счёт, неполный usage, бюджет до отправки,
резервы и месяц, расходы судьи/повтора/ошибки, пересечения категорий, ноль успехов,
pending/пропуски, схемы, эталоны, два запуска, сравнение, целостность, общий lock,
ссылки/отрисовку отчёта и нулевой бюджет. Полное демо дополнительно выполняется
в дочернем процессе без ключей, где fetch и сетевые функции Node.js заблокированы.

Бэкенд-задания пока проверяют **JSON-контракт ответа**, а не серверный код.
Текстовые проверки диагностические и не заменяют проверку смысловых ошибок судьёй.
HTML — только HTML/CSS: кандидатский JavaScript отключён, внешние запросы
заблокированы, профиль браузера временный, окружение без API-ключей. Произвольный
код кандидата в Node.js не исполняется. Полноценная изоляция кодовых проектов —
отдельная работа перед подключением реальных моделей.

На 03.10.2026 `npm audit` сообщает 10 high в транзитивной цепочке promptfoo
(braces, basic-ftp, node-forge и зависимые пакеты). Полного исправления актуальными
версиями нет; автоматическое `audit fix --force` не применялось. Это ограничение
зависимостей зафиксировано, проверка типов и функциональные тесты его не устраняют.

Реальные API, биллинг, субъективные судьи, полный набор 40–50 задач, SQLite,
веб-панель и мониторинг относятся к следующим этапам.
Подробности: [решения](docs/decisions.md), [дорожная карта](docs/roadmap.md).
