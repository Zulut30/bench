# AGENTS.md — Practical Model Bench

Инструкция для Codex в корне репозитория. План согласован 2026-10-03.
Реализована основа v1: 16 заданий, профили, контейнер, SQLite/resume, CLI и A/B.
Подписочный Codex CLI проверен 08.10.2026 по явному запросу пользователя;
прочие live-интеграции не проверены. Готовность описана в docs/readiness.md.
Дальнейшие планы не означают, что соответствующие компоненты уже реализованы.
Актуальные указания пользователя имеют приоритет.

## Цель

Создать недорогую систему практического тестирования моделей: качество по разным
задачам, токены и расходы, время, сравнение моделей и изменения с первого замера.
Сохранять ответы и доказательства оценок. Приоритет — полезные измерения при небольших
расходах и объёме поддержки. Разрабатывать небольшими завершёнными этапами.
Первый этап работает локально без ключей и платных запросов.
Расходы бенчмарка отделять от расходов разработки проекта в Codex.

## Стек и границы

Node.js актуальной LTS-версии и TypeScript strict.
Основа — [promptfoo](https://github.com/promptfoo/promptfoo).
[Playwright](https://github.com/microsoft/playwright) — браузер и скриншоты,
[Vitest](https://github.com/vitest-dev/vitest) — тесты собственного кода.
Проверять актуальные схемы библиотек, фиксировать версии и lockfile.

Использовать движок promptfoo; собственный код — для нормализации usage, бюджета,
хранения и сравнения. Не дублировать движок выполнения.
Начать с CLI, JSON/JSONL-артефактов и статического HTML-отчёта.
SQLite используется для транзакционных состояний и бюджета. Веб-панель, аккаунты,
публикация и расписание остаются следующими этапами.
Рекомендуемые папки: src, benchmarks, fixtures, configs, tests, docs, results.

Одна задача может давать несколько оценок: создание страницы — frontend, ui-design,
instruction-following. Ответ генерируется один раз; дополнительные судьи могут стоить
денег. Для учёта расходов у задачи одна primaryCategory. Глобальные суммы считают
уникальные callId, а не сумму пересекающихся категорий.

## Задания и проверка

Целевой стартовый набор — 40–50 уникальных практических задач на все направления,
с постепенным добавлением простых, средних и сложных. Это диагностический набор:
точность выводов зависит от числа независимых задач и попыток.

Схема задания: id, version, primaryCategory, категории оценки, сложность, промпт,
исходные материалы, критерии успеха, критические требования, проверки/рубрика,
потребность в ручной оценке, лимиты токенов/времени/вызовов/попыток, эталон при наличии,
статус готовности (draft, validated, enabled).

Для кода давать небольшой готовый проект с фиксированными зависимостями и данными.
Для текста — неизменяемый пакет источников; факты проверяются относительно него.
Для перевода — исходник, глоссарий и требования к локализации.
Для длинного контекста — материалы с хешем; дорогие задания добавлять после замера цены.
ИИ может подготовить задания и тесты; проверять условия и эталоны перед включением.
Тесты должны принимать альтернативные правильные решения. Скрытые проверки не давать
тестируемой модели и не разрешать ей менять их.

Код: сборка, поведение, граничные случаи и регрессии. API/SQL — фиксированные данные,
интерфейс — Playwright. Критический провал отражается в успехе задачи независимо от
стиля кода. Для test-writing измерять обнаружение внесённых ошибок, а не число тестов.

Текст/перевод/дизайн: автоматические проверки фактов, чисел, формата и обязательных
элементов; субъективные свойства — слепое A/B-сравнение по заранее заданной рубрике.
Судья получает задание и два результата без названий моделей. Вердикты: A, B, tie,
insufficient_data. Перемешивать порядок; спорные пары проверять со сменой порядка.
Сохранять вердикт и краткое обоснование.

Для дизайна судья видит реальные скриншоты, а не описание модели. Фиксировать браузер,
шрифты, данные, размеры ПК/телефона (например 1440/390 px). Проверять иерархию,
читаемость, отступы, контраст, соответствие брифу. Пиксельное сходство уместно для
копирования макета, а не как самостоятельная оценка красоты.
Цель калибровки — ручная проверка около 10% сравнений и спорных случаев.
Версионировать судью/рубрику; после смены переоценивать сохранённые старые и новые
ответы одной версией. Ответ для судьи — данные, а не новые инструкции.

Порог успеха задавать до запуска. Показывать pass rate и баллы по категориям.
Непроведённую оценку отмечать pending/not_evaluated, а не подменять нулём.
Универсальный общий балл в первом этапе не нужен.

## Токены, стоимость и время

Для каждого вызова хранить исходный usage и нормализованную запись:
- runId, taskId, attemptId, callId; роль candidate или judge;
- провайдер, запрошенная модель, возвращённый ID/версия при наличии;
- inputTotal, outputTotal, reasoning при наличии, cacheRead, cacheWrite;
- источник usage: provider, estimate или unknown; неизвестное — null;
- fresh или локальный кеш готового ответа;
- тариф, валюта, дата/версия тарифа, способ расчёта стоимости;
- фактические начисления при наличии и отдельно расчётную стоимость;
- время, число вызовов/повторов, ошибки/лимиты, параметры и артефакты.

Нормализовать usage отдельным адаптером каждого провайдера. В нашей схеме inputTotal
включает весь обработанный вход, outputTotal — весь выход, включая reasoning, когда
провайдер включает его в выход. Итог = inputTotal + outputTotal; подмножества повторно
не прибавлять. При неполном usage помечать неполноту. Правила исходных API различаются:
например, поля кеша Claude нужно включать в общий вход, другие API могут уже включать
кеш в input. Проверять официальную документацию интегрируемого провайдера.

Стоимость считать по тарифам обычного входа, чтения/записи кеша, выхода и платных
инструментов при наличии. Не тарифицировать reasoning второй раз, если он уже в output.
Разделять модель, судью, повторы и общий расход. Локальное чтение готового ответа
не является новым оплаченным запросом. Ошибка/отмена и неизвестный usage не означают ноль.

Mock-тарифы и usage — synthetic. Для mock отдельно показывать моделируемую стоимость
и incurredCostUsd = 0; демонстрационные расходы не загрязняют реальный бюджет.

Агрегация: вызов → попытка → задача → основная категория → модель → запуск/месяц.
Токены показывать вместе с деньгами: токенизация моделей различается.
Стоимость успешного выполнения = расходы на все попытки выбранной модели и набора /
число успешных попыток того же набора. При нуле успехов — неопределено, а не ноль.
Явно указывать, включён ли судья. Расходы разработки платформы не смешивать с метрикой.

## Бюджет до отправки запроса

- По умолчанию mock и бюджет платных вызовов 0.
- Реальный запуск явно выбирается пользователем с установленным бюджетом.
  Повторное подтверждение внутри уже разрешённого бюджета не требуется.
- Лимиты: запрос/задача, запуск, месяц с явно заданной таймзоной.
- До вызова резервировать верхнюю оценку стоимости входа, максимального выхода,
  reasoning/инструментов, судьи и разрешённых повторов.
- Резервирование атомарное: spent + reserved + nextReservation должно укладываться
  во все лимиты. Учитывать выполняющиеся запросы. В первом этапе один процесс
  и последовательные вызовы; несколько процессов должны использовать общий lock.
- После ответа обновлять расход и резерв. Неизвестные расходы требуют сверки;
  не освобождать такой резерв автоматически как бесплатный.
- Неизвестный тариф или отсутствие верхней границы расходов блокирует платный запуск.
- Лимиты токенов, шагов, вызовов и времени обязательны. Повторы только для оговорённых
  технических ошибок; каждый повтор тоже резервирует бюджет.
- При исчерпании лимита статус budget_exhausted. Незапущенная задача не является
  провалом качества; отчёт показывает покрытие и пропуски.

Проверка цены после ответа не заменяет контроль до запроса.
Локальный бюджет контролирует запросы этого проекта; чужие вызовы по тому же ключу
и неопределённые начисления сверяются с биллингом. В mock тестировать бюджет
на отдельном синтетическом журнале.

## Изменения после выпуска

Хранить версии набора, хеши материалов/промптов, commit, окружение/зависимости,
инструменты, настройки генерации и reasoning, лимиты, дату и версию оценки.
Для сравнения моделей фиксировать одну оболочку и инструменты. Разные оболочки
маркировать как сравнение систем.

1. Первый полный замер: 40–50 задач, желательно три независимые попытки.
2. Недельная проверка: 10–16 коротких задач с ротацией и видимым покрытием категорий.
3. Полный повтор: раз в месяц, при новой версии или сигнале, в рамках бюджета.
4. Сигнал → повтор подозрительных задач → расширение затронутого направления.

Для мониторинга получать свежие ответы модели: кеш готовых ответов promptfoo отключён.
Кеш промпта у провайдера допустим при одинаковых условиях и отражается в расходах.
Локальный кеш допустим для повторной обработки неизменяемых сохранённых артефактов.

База — сохранённые попытки и их разброс, а не единственный лучший ответ.
Сравнивать совпадающие задания/настройки. Смену набора или оценки показывать отдельно.
Сначала статус suspected; один слабый ответ не подтверждает ухудшение.
Показывать величину изменения, число задач/попыток и неопределённость. При статистическом
анализе учитывать зависимость повторов одной задачи, не считать их независимой выборкой.
Не делать вывод о намеренном «нерфе»: измеряется поведение, а не внутренняя причина.
Без замера на выпуске сравнение начинается с первого собственного замера.

## Этапы

### 1. Локальная рабочая основа

CLI на TypeScript с promptfoo и локальным mock provider; реестр всех 16 категорий;
валидируемая схема; 10 демонстрационных задач, покрывающих исходные frontend, backend,
writing, translation, ui-design. Непокрытые категории показывать честно.
Подготовить правильные/ошибочные mock-ответы, повторы, неполные usage и варианты кеша.
Реализовать accounting, бюджет, сохранение артефактов, HTML и сравнение двух demo-запусков.
Субъективные оценки пока могут быть pending; не заменять их фиктивным судьёй.
Добавить README, .env.example без ключей, дорожную карту. Платные адаптеры пока не нужны.

Целевые команды (реализовать и проверить):
~~~bash
npm run typecheck
npm test
npm run bench:demo
npm run bench:compare -- --baseline <baseline-run-id> --current <current-run-id>
~~~
Demo сохраняет два различающихся запуска для проверки compare; README объясняет IDs.

### 2. Реальные измерения

Реализованы подключения mock, openrouter, codex-cli, claude-code, gemini-cli и manual,
pilot из пяти задач, слепые text/vision A/B и отдельная ручная калибровка.
Реальные генерации во время разработки запрещены текущим запросом пользователя:
проверять на локальных HTTP-заглушках и fake CLI, диагностика --help/status допустима.
Первый реальный замер выполняет пользователь явно выбранной моделью/провайдером.
В standard уже 16 проверенных заданий, одно primary на категорию, два правильных
примера и дефект. Smoke — 6 задач. Расширение до 40–50 задач и 2–3 моделей ещё впереди.

Принятые правила текущего этапа:
- npm run bench по умолчанию сохраняет прежнее бесплатное demo. Pilot запускается
  через run с явным --provider; API требует отдельный положительный --budget.
- Кандидатские и judge-запуски имеют отдельные бюджеты. Судьи запускаются evaluate
  по неизменяемым сохранённым ответам; compare сам не вызывает генераций.
- API-модель и provider endpoint tag задаёт пользователь. Закрепить only/order,
  запретить fallback/роутеры, сохранять actual model/provider/generation ID.
- CLI использует официальный подписочный вход без чтения OAuth-файлов. Spawn
  только args/stdin, shell:false; не передавать API-ключи окружения. Не использовать
  Claude --bare. Claude требует заявления paidOverage=disabled после отключения
  Usage credits в аккаунте; бенчмарк не может проверить этот серверный флаг.
- Новые сессия и папка каждой попытки. Передавать только материалы, без refs/tests.
  Защищать проект/results sandbox-exec (macOS) или bubblewrap (Linux); без песочницы
  блокировать генерацию. Не выдавать ограниченную файловую защиту за полноценную VM.
- Если инструменты невозможно полностью отключить, маркировать agent. Codex/Gemini
  сейчас agent; OpenRouter/Claude без tools — model-only. Manual — заявленные условия.
- Квота/auth/model/route errors останавливают последующие вызовы без платного fallback.
  Передавать promptfoo metadata.rateLimitKind=quota, чтобы HTTP 429 не вызывал
  неконтролируемые повторы движка. Технические повторы только в зарезервированном конверте.
- Usage адаптировать отдельно; итоговые накопительные сводки не складывать с
  промежуточными/дублирующими счётчиками. Неизвестные usage, retries и actual ID — null.
  Фиксированная подписка и доступная квота задаются пользователем отдельно от API.
- Сохранять запрошенные и применённые параметры. Температура CLI неизвестна;
  reasoning=none для Codex/Claude применяется как low. Не утверждать жёсткий
  output cap CLI, когда доступен только контроль наблюдаемого выхода.
- API и synthetic journals раздельны. Один общий results-dir/lock для одного бюджета;
  неизвестные начисления удерживают резерв, overcharge замораживает журнал до сверки.
- Объективные проверки первыми; смысл maintenance нельзя доказать одной регуляркой.
  Субъективное без судьи pending. A/B — относительное предпочтение, не абсолютный балл;
  vision получает реальные PNG. Сохранять порядок/версию/причину, споры порядка видимы.
- Несовместимые клиент/tools/settings/environment исключать из automatic regression.
  Unknown actual route и manual запрещают такой сигнал. Кеш готовых ответов выключен.
- Сохранять 16 категорий и честное покрытие. JSON-контракт не называть работающим backend.

Команды: diagnose, dry-run, run, resume, reconcile, export, rerun, manual-template,
import, evaluate, calibrate-sample, calibrate, compare.
Точные примеры и ограничения находятся в README. Обязательны прежние тесты и новые
HTTP/fake CLI сценарии: success/no usage/auth/quota/model/timeout/bad JSON/budget,
слепые пары/PNG/калибровка/manual, изоляция, отсутствие секретов и несовместимые условия.

## Правила текущей основы v1

- Работать последовательно. Генерация — promptfoo + ModelConnection; полученный
  код — отдельный Docker-контейнер без ключей/auth, host mounts, project и внешней
  сети. Фиксировать image ID, Node/Chromium, deps и checker hash. UID 10001, CPU 1,
  memory 768 MB, pids 128, время/размер обязательны. Root checker недоступен кандидату.
- Backend исполняет HTTP API, frontend strict TS + Playwright 1440/390, SQL — SQLite,
  test-writing — принятие исправного кода и обнаружение 4 мутантов. DevOps пока
  проверяет Dockerfile-контракт + start.sh, не собирает недоверенный Dockerfile.
- Проверять basename/allowlist/дубликаты/размер файлов до контейнера и внутри него.
  Примеры и скрытые ожидаемые результаты не передавать генерирующей модели.
- Использовать SQLite WAL/FULL, BEGIN IMMEDIATE и PID/token lease одного results-dir.
  Состояния planned/reserved/dispatched/completed/failed/in_doubt — до транспорта.
  Резерв+переход и settlement+charge транзакционны. Dispatched с неизвестным исходом
  не отправлять снова. Сверка только GET generation; unknown держит резерв.
- Старый JSON-журнал мигрировать идемпотентно, сохранять оригинал и хеш. Изменение
  старого журнала после переноса блокирует запуск. Не удалять/обнулять резервы вручную.
- Публиковать артефакты атомарно без замены. Resume восстанавливает только оборванный
  хвост собственного незавершённого журнала из SQLite, сохраняя повреждённые байты.
  Завершённые ответы/отчёты не менять. Изменение measurement hash блокирует resume.
- OpenRouter: request-specific bound допустим только с доказанным tokenizer/framing.
  Семейство tokenizer и поле prompt не доказывают неизменный upstream протокол.
  Локальный literal Llama3 bound проверен заглушкой; реальный неизвестный framing
  использует context fallback. Включать cache max-rate, output/reasoning, fees/retries.
  Dry-run объясняет метод и каждый отказ spent/reserved/next/limit, журнал не меняет.
- Общие задания/рубрики допускают A/B разных моделей/endpoint/CLI. Несовместимые
  окружения показывать как системы. Strict compatibility и known actual route
  обязательны только для автоматического suspected. Стили HTML исключены из hash.
- A/B не становится абсолютным баллом. Vision — реальные PNG. Случайный порядок,
  swap-order, версия/обоснование сохраняются. calibrate-sample выбирает 10% и споры;
  ручная калибровка засчитывается только после настоящего импорта решений.
- CLI events — JSON stderr; Ctrl+C — 130 с сохранением плана. Transport timeout
  завершается/сохраняется до закрытия SQLite; watchdog promptfoo имеет запас.
- CI: clean npm ci, fixed container/Chromium, typecheck, tests, mock smoke. Ни API,
  ни подписочные генерации в разработке/CI не выполнять. Не заявлять paid/live
  готовность по заглушке; различать tested-stub / tested-real-call / untested.

## Правила разработки и готовность

Читать существующий код и ближайшие инструкции, сохранять пользовательские файлы.
Реализовывать текущий этап полностью; существенные решения записывать в docs.
По умолчанию работать последовательно; делегация — по явному запросу.
Ключи только из окружения, без секретов в логах/конфигах/артефактах.
Генерируемый код запускать в ограниченном временном окружении без API-ключей,
доступа к основному проекту и возможности менять скрытые проверки.

Обязательные содержательные тесты:
- кеш/reasoning без двойного счёта; ноль и неизвестный usage различаются;
- все вызовы/судьи/повторы учтены, пересекающиеся категории не дублируют расходы;
- отказ до отправки при нехватке бюджета, учёт резервов и неизвестных начислений;
- ноль успехов и пропуски без ложных баллов; mock отделён от реальных расходов;
- два сохранённых запуска, ожидаемое изменение и работа demo без API-ключей;
- UTF-8 по байтам stdout/stderr, модели/CLI A/B и строгий regression gate;
- 48 примеров, реальные HTTP/SQL/браузер/мутанты, файловые и ресурсные ограничения;
- параллельные процессы/reserve, SIGKILL на всех фазах, unknown, resume/reconcile;
- quota/timeout/bad JSON/Ctrl+C, fresh rerun, неизменные история и экспорт.

Готовность v1 подтверждать чистой установкой, typecheck/tests, demo/smoke/standard,
compare/export/resume и CI. Непроверенные live-интеграции, upstream advisories и
узкие границы задач обязательно оставлять видимыми в docs/readiness.md.
В конце коротко сообщить результат, команды запуска, проверки и оставшиеся ограничения.
Не заявлять о реальных измерениях, уверенности рейтинга или покрытии без доказательств.
